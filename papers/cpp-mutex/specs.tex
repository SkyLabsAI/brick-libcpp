We begin by examining \lstinline{std::mutex}, the basic lock class. The class contains methods \lstinline{lock}, \lstinline{unlock}, and \lstinline{try_lock}, as well as a constructor and destructor. The intended behavior is simply to provide mutual exclusion; a simple implementation could be a spinlock as shown in Figure~\ref{mutex-simple}, although more realistic implementations use OS primitives for efficiency. While \lstinline{std::mutex} is the library class corresponding to a standard lock, its informal specification has three restrictions that do not appear in the standard separation logic treatment:
\begin{itemize}
\item When a thread calls \lstinline{unlock}, it must own the mutex (i.e., it must have been the thread that most recently called \lstinline{lock}).
\item When a thread calls \lstinline{lock}, it must \emph{not} own the mutex.
\item When a mutex is destroyed, it must not be owned by any threads.
\end{itemize}
A program that violates any of these conditions has \emph{undefined behavior} according to the library specification, so our program logic must ensure that they are respected. %include checks in toy implementation, or just mention that they could be added?

The representation for a mutex has the same shape as a standard lock: we write $m \mapsto \mutex{\gamma}{P}$ for a mutex at $m$ associated with ghost identifier $\gamma$ and protected resources $P$. However, we must extend the specifications of the mutex operations to enforce the requirements above. One of the original selling points of CSL was that it could naturally verify \emph{daring} concurrency patterns~\cite{csl} in which a lock acquired by one thread is released by another; in fact, in ordinary separation logics every predicate is freely transferable between threads. Fortunately, as mentioned in Section~\ref{brick}, the design of the BRiCk logic supports a non-transferable predicate $\currentthread{t}$ asserting that the current thread is $t$, which we can use to tie resources to a specific thread. When a thread $t$ starts using the mutex, it will generate a predicate $\notlocked{\gamma}{t}$, which it exchanges for another predicate $\locked{\gamma}{t}$ when it locks the mutex. A matching predicate $\usedthreads{\gamma}{T}$ will hold the set of all threads that are currently using the mutex, and the precondition of the destructor will require $\usedthreads{\gamma}{\emptyset}$, ensuring that no thread currently holds the lock. Formally, these predicates satisfy the following properties:
%make this a figure?
\begin{mathpar}
\inferrule{t \not\in T}{\usedthreads{\gamma}{T} \vs \usedthreads{\gamma}{T \cup \{t\}} \ast \notlocked{\gamma}{t}} \and
\usedthreads{\gamma}{T} \ast \notlocked{\gamma}{t} \vdash t \in T \and
\usedthreads{\gamma}{T} \ast \notlocked{\gamma}{t} \vs \usedthreads{\gamma}{T \setminus \{t\}} \and
\notlocked{\gamma}{t} \ast \notlocked{\gamma}{t} \vdash \mathsf{False} \and \notlocked{\gamma}{t} \ast \locked{\gamma}{t} \vdash \mathsf{False} \and \locked{\gamma}{t_1} \ast \locked{\gamma}{t_2} \vdash \mathsf{False} %anything else we need?
\end{mathpar}
This user-tracking pattern is very useful for describing thread-specific properties of mutexes; we will extend it for the following mutex types, and explain its implementation in Section~\ref{login}.

We can then specify the mutex as follows:
\[\begin{array}{c}
\{\later P\}\\ \texttt{mutex()}\\ \{\exists \gamma.\ \mutex{\gamma}{P} \ast \usedthreads{\gamma}{\emptyset}\} \vspace{1em}\\%constructor notation?
\{\currentthread{t} \ast m \mapsto_q \mutex{\gamma}{P}\ast\notlocked{\gamma}{t}\}\\ {m\texttt{.lock()}} \\ \{m \mapsto_q \mutex{\gamma}{P}\ast P\ast\locked{\gamma}{t}\}  \vspace{1em}\\
    \{\currentthread{t} \ast m \mapsto_q \mutex{\gamma}{P}\ast\locked{\gamma}{t}
      \ast\triangleright P\}\\ {m\texttt{.unlock}()}\\
    \{m \mapsto_q \mutex{\gamma}{P}\ast\notlocked{\gamma}{t}\}  \vspace{1em} \\
\{m \mapsto \mutex{\gamma}{P} \ast \usedthreads{\gamma}{\emptyset}\}\\ \sim m()\\ \{P\} %destructor notation?
\end{array}\]
A thread $t$ exchanges $\notlocked{\gamma}{t}$ for $\locked{\gamma}{t}$ when acquiring the mutex and vice versa when releasing; these predicates are freely transferable, but $\currentthread{t}$ ensures that each thread holds its own predicate when calling \lstinline{lock} or \lstinline{unlock}, and the laws of $\mathsf{locked}$ and $\mathsf{not\_locked}$ ensure that no two threads hold the mutex at once\kedu{at most once?} and that a thread cannot simultaneously be $\mathsf{locked}$ and $\mathsf{not\_locked}$. Finally, the $\usedthreads{\gamma}{\emptyset}$ in the precondition of the destructor ensures that all threads have been removed from the set of users (and thus cannot hold the mutex) before deallocation. When these specifications are used in proofs, the thread that allocates the mutex will acquire and hold $\usedthreads{\gamma}{T}$, and generate a $\notlocked{\gamma}{t}$ predicate for each thread $t$ participating in the mutex; when those threads terminate, the main thread will recollect all the $\notlocked{}{}$ predicates and remove them from $\usedthreads{}{}$ before the mutex is destroyed. %example proof?

\subsection{\texorpdfstring{\lstinline{std::recursive_mutex}}{std::recursive\_mutex}}
\emph{Recursive} or \emph{reentrant} mutexes can be acquired multiple times by the same thread, and only become available to another thread once every acquire has been matched with a release. Recursive mutexes are popular in object-oriented programming, allowing a method to acquire a lock every time it is called even if it is called from another locked method. A canonical recursive mutex implementation is shown in Figure~\ref{rmutex-simple}. When no thread holds the lock, \lstinline{count} is 0 and \lstinline{owner} is \lstinline{null}. When a thread that does not already own the lock tries to acquire it, it calls the \lstinline{lock} method of an underlying conventional mutex; likewise, when the owner releases the lock for the last time (\lstinline{count} is 1), it \lstinline{unlock}s the underlying mutex. However, when the owner re-acquires a lock it already owns, it performs no synchronization operations, instead simply incrementing the count---and likewise, a non-final release simply decrements the count. This avoids redundant synchronization and deadlock while still providing mutual exclusion. %note that an implementation requires a get-thread-id function

\begin{figure}[htb]
\begin{lstlisting}
std::atomic<std::thread::id> owner; // default val neq any thread ID
int count;
std::mutex m;

void lock(){
  if(owner != get_id()){
    m.lock();
    owner = get_id();
  }
  count++;
}

void unlock(){
  count--;
  if(count == 0){
    m.unlock();
    owner = std::thread::id{}; // reset to default
  }
}
\end{lstlisting}
\caption{A simple implementation of \lstinline{std::recursive_mutex}}
\label{rmutex-simple}
\end{figure}

The specification of a recursive mutex in separation logic requires some care, since acquiring/releasing the mutex may or may not obtain/give up the lock resources depending on how many times the caller has previously acquired it. While we could give specifications that explicitly distinguish the two cases, this is contrary to the intended abstraction---the point of a recursive mutex is that whether or not we hold the mutex before acquiring it, we know that we hold it afterwards, and as long as we perform the same number of releases as acquires we do not need to account for whether we still hold the lock. %note the existence of both atomic and invariant-based specs, and their relationship?

We accomplish this by replacing the $\mathsf{not\_locked}$ and $\mathsf{locked}$ predicates of the mutex with a single predicate of the form $\acquirable{\gamma}{t}{n}{P}$, where $n$ is the number of times (0 or more) that $t$ holds the mutex. When $n$ is 0, $\mathsf{holds}$ acts as $\mathsf{not\_locked}$, and can be generated by or removed from $\usedthreads{}{}$. When $n$ is greater than 0, $\mathsf{holds}$ acts as $\mathsf{locked}$: it is exclusive with any other non-zero $\mathsf{holds}$, and the owner can borrow the resources $P$ from it. This lets us specify \lstinline{lock} and \lstinline{unlock} as simply increasing and decreasing $n$, respectively:
\[\begin{array}{c}
\{\currentthread{t} \ast m \mapsto_q \rmutex{\gamma}{P}\ast\acquirable{\gamma}{t}{n}{P}\}\\ {m\texttt{.lock()}} \\ \{m \mapsto_q \rmutex{\gamma}{P}\ast P\ast\acquirable{\gamma}{t}{n+1}{P}\}  \vspace{1em}\\
    \{\currentthread{t} \ast m \mapsto_q \rmutex{\gamma}{P}\ast\acquirable{\gamma}{t}{n+1}{P}\}\\ {m\texttt{.unlock}()}\\
    \{m \mapsto_q \rmutex{\gamma}{P}\ast\acquirable{\gamma}{t}{n}{P}\}
\end{array}\]
These rules do not explicitly obtain or give up $P$; instead, $\mathsf{holds}$ has the property that
\[\inferrule{n > 0}{\acquirable{\gamma}{t}{n}{P} \dashv\vdash P \ast (P \wand \acquirable{\gamma}{t}{n}{P})}\]
allowing a thread to borrow $P$ as long as it can prove it owns the mutex at least once. This allows the reasoning pattern where a method acquires a recursive mutex, manipulates the associated resources, and releases the mutex, without ever having to do case analysis on whether the caller already owned the mutex. %mention fixed argument to P? %example?

\subsection{\texorpdfstring{\lstinline{std::shared_mutex}}{std::shared\_mutex}}

C++'s \lstinline{shared_mutex} class is more commonly known as a \emph{reader-writer lock}. It provides two separate pairs of acquire and release operations, \emph{exclusive} \lstinline{lock}/\lstinline{unlock} and \emph{shared} \lstinline{lock_shared}/\lstinline{unlock_shared}; while \lstinline{lock} and \lstinline{unlock} ensure mutual exclusion, any number of threads can successfully perform \lstinline{lock_shared} at once as long as no thread has acquired the lock exclusively. Reader-writer locks have been modeled in separation logic by \citet{heaplang-rw-lock}, and we build on their work, but must also account for C++'s additional restrictions: no thread may acquire shared ownership of the mutex more than once, and only threads that have acquired it may release it.

\begin{figure}[htb]
\begin{lstlisting} %not sure whether this is the right canonical implementation

std::atomic<int> sharers{0};

void lock(){
  int idle = 0;
  while(!sharers.compare_exchange_strong(idle, -1)) { idle = 0; }
}

void unlock(){
  sharers = 0;
}

void lock_shared(){
  int val;
  do { val = sharers; }
  while(val < 0 || !sharers.compare_exchange_strong(val, val + 1)) {}
}

void unlock_shared(){
  sharers--;
}
\end{lstlisting}
\caption{A simple implementation of \lstinline{std::shared_mutex}}
\label{smutex-simple}
\end{figure}

Following \citet{heaplang-rw-lock}, we take the resource $P$ protected by a shared mutex to be a fractional predicate;
calling \lstinline{lock} yields full ownership of the resource $P(1)$,
while calling \lstinline{lock_shared} yields $P(q)$ for an arbitrary fraction $q$, representing read-only access to $P$.
Accordingly, in our specifications each user of a shared mutex has one of three predicates, $\notlocked{\gamma}{t}$, $\readerlocked{\gamma}{t}{q}$, or $\locked{\gamma}{t}$, where $\mathsf{reader\_locked}$ records the fraction $q$ of ownership received by the reader.

\[
\begin{array}{@{}c@{}}
\{m \mapsto_q \smutex{\gamma}{P}\ast\notlocked{\gamma}{t}\} \\
  m\texttt{.lock()}\ \currentthread{\ t} \\[-1pt]
\{m \mapsto_q \smutex{\gamma}{P}\ast P(1)\ast\locked{\gamma}{t}\} \\[1.8em]
\{m \mapsto_q \smutex{\gamma}{P}\ast\locked{\gamma}{t}\ast\triangleright P(1)\}\\
  m\texttt{.unlock()}\ \currentthread{\ t} \\[-1pt]
\{m \mapsto_q \smutex{\gamma}{P}\ast\notlocked{\gamma}{t}\} \\[1.8em]
\{m \mapsto_q \smutex{\gamma}{P}\ast\notlocked{\gamma}{t}\}\\
  m\texttt{.lock\_shared()}\ \currentthread{\ t} \\[-1pt]
\{m \mapsto_q \smutex{\gamma}{P}\ast\exists q_P.\;P(q_P)\ast\readerlocked{\gamma}{t}{q_P}\} \\[1.8em]
\{m \mapsto_q \smutex{\gamma}{P}\ast\readerlocked{\gamma}{t}{q_P}
  \ast\triangleright P(q_P)\} \\[-1pt]
  m\texttt{.unlock\_shared()}\ \currentthread{\ t} \\
\{m \mapsto_q \smutex{\gamma}{P}\ast\notlocked{\gamma}{t}\}
\end{array}
\]

The $\mathsf{not\_locked}$ ghost state provides an interface that allows a thread to acquire
locked resources at most once regardless of the mutex kinds. Each flavor of mutex
is associated with a disjoint set of thread IDs, managed by one
authoritative piece \allusers\ and fragment pieces \notlocked{\gamma}{t}:
\begin{align*}
  \allusers^{\gamma}(T)
    &\eqdef \mathsf{own}^{\gamma}(\mathord{\bullet}T), \\
  % \mathsf{users}^{\gamma}(T)
  %   &\eqdef \mathsf{own}^{\gamma}(\mathord{\circ}T), \\
  \mathsf{not\_locked}^{\gamma}(t)
    &\eqdef \mathsf{own}^{\gamma}(\mathord{\circ}\{t\}).
\end{align*}
The \allusers{T} ghost state tracks all "logged-in" threads $T$. Each thread with thread ID $t$ can get
a \notlocked{\gamma}{t} handle for that mutex with the \texttt{login} rule, and the handle is
unique for each thread (not-locked-unique). The mutex invariants are slightly
different for different kinds of mutexes, but they all ensure that a thread
must trade in its unique \notlocked{\gamma}{t} handle to acquire protected resources.
This ensures that a thread can't acquire protected resources if it already has
some, and unsafe programs that calls \texttt{mutex.lock()} or
\texttt{shared\_mutex.lock\_shared()} twice consecutively in a single thread
would get stuck. Notably, for recursive mutexes, if a thread already has the
resource, it is safe to \texttt{lock()} again, and the thread simply does not
exchange anything with the invariant.

A thread can also "logout" and turn in its \notlocked{\gamma}{t} handle. Deallocation
of any kind of mutex requires no "logged-in" users
($\allusers^{\gamma}(\varnothing)$), enforcing that any allocated
\notlocked{\gamma}{t} handle is deallocated with \texttt{logout}
(\texttt{all-not\_locked-logged-out}), and so the mutex is not held
by any thread, thus safe to deallocate.

\subsection{Generic \lstinline{lock} and \lstinline{unlock}}
The \lstinline{BasicLockable} named requirement describes the common interface
of types that provide \lstinline{lock()} and \lstinline{unlock()}
operations~\cite{ISO:2024:IIP}.  An invocation of \lstinline{lock()} blocks
until the calling thread acquires the lock, and \lstinline{unlock()} releases a
lock owned by the calling thread.  The caller must not already own the lock
when invoking \lstinline{lock()}, and must own it when invoking
\lstinline{unlock()}.  This is a requirement on a type, rather than a concrete
C++ class: \lstinline{std::mutex}, \lstinline{std::recursive_mutex}, and
user-defined lock types can all implement it.  Generic classes such as
\lstinline{lock_guard} can therefore operate on any such implementation.

We represent an implementation of \lstinline{BasicLockable} by a predicate
$R(q,x)$ describing fractional ownership $q$ of a lock with abstract state
$x$, together with two predicates $L(m,x,K)$ and $U(m,x,K)$.  These predicates
give the resources required to lock and unlock the object at $m$ and describe
their result through the continuation $K$.  The generic specifications are:
\begin{mathpar}
  \spectriple
    {m\mapsto R(q,x)\ast L(m,x,K)}
    {\texttt{m.lock()}}
    {m\mapsto R(q,x)\ast K}

  \spectriple
    {m\mapsto R(q,x)\ast U(m,x,K)}
    {\texttt{m.unlock()}}
    {m\mapsto R(q,x)\ast K}
\end{mathpar}
The representation predicate is preserved by both operations, while the
implementation-specific predicates describe the change in logical ownership.
For example, the \lstinline{std::mutex} instance defines $L$ to exchange the
calling thread's $\mathsf{not\_locked}$ token for the protected resource and its
\texttt{locked} token; it defines $U$ to perform the reverse exchange.  The
recursive and shared mutexes instantiate the same interface with their own
ghost states.  Thus clients can use the two generic specifications without
depending on the particular mutex representation.
