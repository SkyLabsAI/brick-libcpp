We begin by examining \lstinline{std::mutex}, the basic lock class. The class contains methods \lstinline{lock}, \lstinline{unlock}, and \lstinline{try_lock}, as well as a constructor and destructor. The intended behavior is simply to provide mutual exclusion; a simple implementation could be a spinlock as shown in Figure~\ref{mutex-simple}, although more realistic implementations use OS primitives for efficiency. While \lstinline{std::mutex} is the library class corresponding to a standard lock, its informal specification has three restrictions that do not appear in the standard separation logic treatment:
\begin{enumerate}
\item When a thread calls \lstinline{unlock}, it must own the mutex (i.e., it must have been the thread that most recently called \lstinline{lock}).
\item When a thread calls \lstinline{lock}, it must \emph{not} own the mutex.
\item When a mutex is destroyed, it must not be owned by any threads.
\end{enumerate}
A program that violates any of these conditions has \emph{undefined behavior} according to the library specification, so our program logic must ensure that they are respected. %include checks in toy implementation, or just mention that they could be added?

The representation predicate for a mutex has the same shape as a standard lock: we write $m \mapsto \mutex{\gamma}{P}$ for a mutex at $m$ associated with ghost identifier $\gamma$ and protected resources $P$. However, we must extend the specifications of the mutex operations to enforce the requirements above. The third property is the simplest from a separation logic perspective: we can define a fractional resource $\token{}{q}$ that a thread must give up in order to acquire the mutex, and require full ownership $\token{}{1}$ in the precondition of the destructor. The first two properties are more complicated, since they check whether a thread performing an operation is \emph{the same thread} as one that performed a previous operation. Our basic approach is to define predicates $\notlocked{\gamma}{t}{q}$ and $\locked{\gamma}{t}{q}$ such that a thread $t$ exchanges $\notlocked{\gamma}{t}{q}$ for $\locked{\gamma}{t}{q}$ when acquiring the mutex, and vice versa when releasing it. However, these predicates, like any other CSL predicate, can be transferred between threads when they synchronize: how can we ensure that the thread that owns $\notlocked{\gamma}{t}{q}$ is actually thread $t$? For this, we use BRiCk's non-transferable predicate $\currentthread{t}$ described in Section~\ref{brick}: a thread must own both $\currentthread{t}$ and $\notlocked{\gamma}{t}{q}$ (resp. $\locked{\gamma}{t}{q}$) to acquire (resp. release) the mutex, proving that it is in fact the thread identified by the predicate. These predicates satisfy the following properties:
%make this a figure?
\begin{mathpar}
\notlocked{\gamma}{t}{q_1} \ast \notlocked{\gamma}{t}{q_2} \vdash \mathsf{False} \and %\notlocked{\gamma}{t} \ast \locked{\gamma}{t} \vdash \mathsf{False} \and
\locked{\gamma}{t_1}{q_1} \ast \locked{\gamma}{t_2}{q_2} \vdash \mathsf{False}
\and \token{\gamma}{1} \ast \locked{\gamma}{t}{q} \vdash \mathsf{False} %anything else we need?
\end{mathpar} %explain a little more, and explain view shifts

How does a thread obtain $\notlocked{\gamma}{t}{q}$ to begin with? We could explicitly specify a set of threads that are allowed to use a mutex when it is created, but we may not know this set of threads in advance and it may even be unbounded (e.g., if we spawn threads in a loop). Instead, we make it possible for a thread $t$ to \emph{register} itself with an existing mutex $\gamma$ and obtain $\notlocked{\gamma}{t}{q}$, as long as $t$ can guarantee that it is not already registered with $\gamma$. Each thread holds a set of as-yet-unregistered mutex names $\mutexperm{t}{A}$, where $A$ is initially the universe of possible mutex names $\top$. When $t$ wishes to register with a mutex $\gamma$, it removes the name of $\gamma$ from $A$ and exchanges it (along with a share of $\mathsf{token}$) for $\mathsf{not\_locked}$:
\[ \mutexperm{t}{\mutexname{\gamma}} \ast \token{\gamma}{q} \dashv \vdash \notlocked{\gamma}{t}{q} \]
When a thread is finished using the mutex (and does not currently hold it), it can perform the same operation in reverse to recover $\mutexperm{t}{\mutexname{\gamma}}$ and $\token{\gamma}{q}$.
This name-tracking pattern is very useful for describing thread-specific properties of mutexes; we will extend it for the following mutex types, and explain its implementation in Section~\ref{login}.

Using the $\mathsf{m\_locked}$ and $\mathsf{not\_locked}$ predicates, we can specify the mutex as follows:

A thread $t$ exchanges $\notlocked{\gamma}{t}{q}$ for $\locked{\gamma}{t}{q}$ when acquiring the mutex and vice versa when releasing; $\currentthread{t}$ ensures that each thread holds its own predicate when calling \lstinline{lock} or \lstinline{unlock}%, and the laws of $\mathsf{m\_locked}$ and $\mathsf{not\_locked}$ ensure that no two threads hold the mutex at once and that a thread cannot simultaneously be $\mathsf{m\_locked}$ and $\mathsf{not\_locked}$
. Finally, $\token{\gamma}{1}$ in the precondition of the destructor ensures that no threads hold the mutex before deallocation. %When these specifications are used in proofs, the thread that allocates the mutex will acquire and hold $\usedthreads{\gamma}{T}$, and generate a $\notlocked{\gamma}{t}$ predicate for each thread $t$ participating in the mutex; when those threads terminate, the main thread will recollect all the $\notlocked{}{}$ predicates and remove them from $\usedthreads{}{}$ before the mutex is destroyed.

Figure~\ref{mutex-ex} shows a simple application of \lstinline{mutex}. The mutex \lstinline{m} protects the variable \lstinline{x}, which is incremented by two separate threads. We sketch a proof with the lock invariant $P \triangleq \exists n.\ \texttt{x} \mapsto n \ast \mathsf{even}(n)$; we could use ghost state to show that \lstinline{x} is exactly 4 at the end of the program, but this is orthogonal to the novelties of our mutex specification. The proof is outlined in Figure~\ref{mutex-ex-proof}. When the main thread spawns a new thread executing \lstinline{double_incr}, it gives the new thread partial ownership of the mutex and its token; it retains $\currentthread{t_0}$ or $\mutexperm{t_0}{\top}$, and the new thread receives its own thread-specific resources when spawned. Before calling \lstinline{m.lock}, each thread registers with the mutex, exchanging $\mutexperm{}{\mutexname{\gamma}}$ and a piece of the token for a $\mathsf{not\_locked}$ predicate. When a thread locks \lstinline{m} it exchanges its $\mathsf{not\_locked}$ for $\mathsf{m\_locked}$ and ownership of $P$; unlocking \lstinline{m} performs the same operation in reverse. After each thread finishes using \lstinline{m}, it unregisters and recovers its token and mutex permission.
Finally, the main thread joins with the spawned thread and recollects its shares of the mutex and token; the full $\token{\gamma}{1}$ guarantees that no thread holds the lock, satisfying the precondition of \lstinline{m}'s destructor.

\subsection{\texorpdfstring{\lstinline{std::recursive_mutex}}{std::recursive\_mutex}}
\emph{Recursive} or \emph{reentrant} mutexes can be acquired multiple times by the same thread, and only become available to another thread once every acquire has been matched with a release. Recursive mutexes are popular in object-oriented programming, allowing a method to acquire a lock every time it is called even if it is called from another locked method. A canonical recursive mutex implementation is shown in Figure~\ref{rmutex-simple}. When no thread holds the lock, \lstinline{count} is 0 and \lstinline{owner} is \lstinline{null}. When a thread that does not already own the lock tries to acquire it, it calls the \lstinline{lock} method of an underlying conventional mutex; likewise, when the owner releases the lock for the last time (\lstinline{count} is 1), it \lstinline{unlock}s the underlying mutex. However, when the owner re-acquires a lock it already owns, it performs no synchronization operations, instead simply incrementing the count---and likewise, a non-final release simply decrements the count. This avoids redundant synchronization and deadlock while still providing mutual exclusion. %note that an implementation requires a get-thread-id function %note that there's no natural daring version of the recursive mutex---only the thread ID distinguishes re-acquisition from mutex-breaking

\begin{figure}[htb]
\begin{lstlisting}
std::atomic<std::thread::id> owner;
int count;
std::mutex m;

void lock(){
  if(owner != get_id()){
    m.lock();
    owner = get_id();
  }
  count++;
}

void unlock(){
  count--;
  if(count == 0){
    m.unlock();
    owner = std::thread::id{}; // reset to default
  }
}
\end{lstlisting}
\caption{A simple implementation of \lstinline{std::recursive_mutex}}
\label{rmutex-simple}
\end{figure}

The specification of a recursive mutex in separation logic requires some care, since acquiring/releasing the mutex may or may not obtain/give up the lock resources depending on how many times the caller has previously acquired it. While we could give specifications that explicitly distinguish the two cases, this is contrary to the intended abstraction---the point of a recursive mutex is that whether or not we hold the mutex before acquiring it, we know that we hold it afterwards, and as long as we perform the same number of releases as acquires we do not need to account for whether we still hold the lock. %note the existence of both atomic and invariant-based specs, and their relationship?

We accomplish this by replacing the $\mathsf{not\_locked}$ and $\mathsf{locked}$ predicates of the mutex with a single predicate of the form $\acquirable{\gamma}{t}{n}{P}{a}$, where $n$ is the number of times (0 or more) that $t$ holds the mutex. When $n$ is 0, $\mathsf{holds}$ acts as $\mathsf{not\_locked}$, and can be generated by or removed from $\usedthreads{}{}$. When $n$ is greater than 0, $\mathsf{holds}$ acts as $\mathsf{locked}$: it is exclusive with any other non-zero $\mathsf{holds}$, and the owner can borrow the resources $P$ from it via the rule:
\[\inferrule{n > 0}{\acquirable{\gamma}{t}{n}{P}{a} \vdash P(a) \ast (\forall a'.\ P(a') \wand \acquirable{\gamma}{t}{n}{P}{a'})}\]
This rule also illustrates the role of the argument $a$. Protected resources are often existentially quantified, e.g., $\exists v.\ x \mapsto v$, which interacts poorly with borrowing: a thread that holds the lock has complete control over the value $v$, but returning and then re-borrowing the resource will re-quantify over $v$, losing track of whatever value it currently has. We solve this by making $P$ a predicate on an arbitrary argument type, and making the current argument value $a$ a parameter to $\mathsf{holds}$; as long as a thread holds the mutex, it knows the exact value of $a$, but when $n = 0$ the value of $a$ is arbitrary and gives no information about the state of the protected resources. %return to this explanation

Using $\mathsf{holds}$, we can specify \lstinline{lock} and \lstinline{unlock} as simply increasing and decreasing $n$, respectively:
\[\begin{array}{c}
\{\currentthread{t} \ast m \mapsto_q \rmutex{\gamma}{P}\ast\acquirable{\gamma}{t}{n}{P}{a}\}\\ {\texttt{m.lock()}} \\ \{m \mapsto_q \rmutex{\gamma}{P}\ast \exists a'.\ \mathsf{acquire}(n, a, a') \ast \acquirable{\gamma}{t}{n+1}{P}{a'}\}  \vspace{1em}\\
    \{\currentthread{t} \ast m \mapsto_q \rmutex{\gamma}{P}\ast\acquirable{\gamma}{t}{n+1}{P}{a}\}\\ {\texttt{m.unlock}()}\\
    \{m \mapsto_q \rmutex{\gamma}{P}\ast\acquirable{\gamma}{t}{n}{P}{a}\}
\end{array}\]
where $\mathsf{acquire}(n, a, a') \triangleq (n > 0 \Rightarrow a' = a)$ allows the argument $a$ to change arbitrarily if the caller of \lstinline{lock} did not already own the lock, but enforces that $a$ is unchanged if the caller did already own the lock. Other than that, these specifications are entirely agnostic to whether any given call is the first \lstinline{lock} or last \lstinline{unlock} on the mutex: we can thus reason about a method that acquires a recursive mutex, manipulates the associated resources, and releases the mutex without ever having to do case analysis on whether the caller already owned the mutex.

Figure~\ref{rmutex-ex} shows an example of the use of \lstinline{recursive_mutex}. The mutex \lstinline{m} protects both \lstinline{balance_a} and \lstinline{balance_b}, and is acquired in each of their update methods. The \lstinline{transfer} method atomically transfers the amount \lstinline{x} from \lstinline{balance_b} to \lstinline{balance_a}---no other client should be able to observe a state in which \lstinline{balance_a} has been increased by \lstinline{balance_b} has not been decreased---so \lstinline{transfer} also acquires \lstinline{m}. The \lstinline{update_a} and \lstinline{update_b} methods may be called either from inside \lstinline{transfer} or directly by a client; the recursive mutex allows them to safely acquire \lstinline{m} in either case, and restore it to its previous state before returning.

The proof of the example is sketched in Figure~\ref{rmutex-ex-proof}. The protected resources are $P(a, b) \triangleq \texttt{balance\_a} \mapsto a \ast \texttt{balance\_b} \mapsto b$. The specifications of \lstinline{update_a} and \lstinline{update_b} take advantage of the dual meaning of the $\mathsf{holds}$ predicate's argument: if the caller already owns \texttt{m} then it learns that the value of \lstinline{balance_a} or \lstinline{balance_b} has been increased, while if it does not then it loses ownership of $P$ and the argument values give no information. In the body of \lstinline{transfer}, because we have already \lstinline{lock}ed \lstinline{m}, we know the precise values of \lstinline{balance_a} and \lstinline{balance_b} and can guarantee that they are $a + x$ and $b - x$ before \lstinline{unlock}ing, as desired.

\subsection{\texorpdfstring{\lstinline{std::shared_mutex}}{std::shared\_mutex}}

C++'s \lstinline{shared_mutex} class is more commonly known as a \emph{reader-writer lock}. It provides two separate pairs of acquire and release operations, \emph{exclusive} \lstinline{lock}/\lstinline{unlock} and \emph{shared} \lstinline{lock_shared}/\lstinline{unlock_shared}; while \lstinline{lock} and \lstinline{unlock} ensure mutual exclusion, any number of threads can successfully perform \lstinline{lock_shared} at once as long as no thread has acquired the lock exclusively. Reader-writer locks have been modeled in separation logic by \citet{heaplang-rw-lock}, and we build on their work, but must also account for C++'s additional restrictions: no thread may acquire shared ownership of the mutex more than once, and only threads that have acquired it may release it.

Following \citet{heaplang-rw-lock}, we take the resource $P$ protected by a shared mutex to be a fractional predicate;
calling \lstinline{lock} yields full ownership of the resource $P(1)$,
while calling \lstinline{lock_shared} yields $P(q)$ for an arbitrary fraction $q$, representing read-only access to $P$.

\section{Implementing the Mutex Specifications}
Our specifications of C++ mutexes capture the informal specifications of the mutexes and can be used to verify client programs. Ideally, we would next show that standard library implementations actually meet our specifications. However, the widely used implementations of the C++ standard library would be difficult to verify---they use Pthread implementations of the corresponding mutex types, which have nearly the same specifications as the standard library mutexes, and the Pthread implementations in turn make heavy use of operating system primitives with complicated low-level specifications (e.g., Linux's \lstinline{futex}). In this section, we instead verify simple and portable implementations of the mutexes that synchronize using atomic operations instead of OS primitives.\kedu{Do we want to explain why we think they are functionally equivalent?} We first describe the ghost state construction that underlies the $\mathsf{locked}$ and $\mathsf{not\_locked}$ predicates for each mutex, and then show that our simple implementation of each mutex meets the specifications of the previous section.

\subsection{The Mutex Name Library}
\label{login}

All three of our mutex specifications use thread-specific predicates ($\mathsf{not\_locked}$, $\mathsf{m\_locked}$, $\mathsf{holds}$, etc.) to enforce the mutexes' requirements on thread behavior. In this section we describe a general ghost construction that we use to implement all of our thread-specific predicates. In order to register itself with a mutex and obtain its $\mathsf{not\_locked}$ predicate (or $\mathsf{holds}(0)$ for a recursive mutex), a thread needs to prove that it does not own that mutex: in separation-logic terms, it needs to own a resource demonstrating that it is not the current holder of the mutex. This means that each thread must own, or be able to create, a not-the-owner resource (call it a ``mutex permission'' \kedu{"mutex deposit"?}) %name?
for every mutex it does not currently hold. We model this using an assertion $\mutexperm{t}{A}$, where $A$ is a set of possible mutex names; %mention that it could be expanded beyond mutexes
each thread begins with $A = \top$.

In Iris, we can implement this assertion using resource algebras (RAs), specifically the RA of functions from thread IDs to disjoint infinite sets. The thread creation library holds the resource $\ownGhost{}{\lambda t.\ \text{if } t \in T \text{ then } \emptyset \text{ else } \top}$, where $T$ is the set of currently existing thread IDs; each time we spawn a new thread $t_i$, we add $t_i$ to $T$ and withdraw the singleton function $\ownGhost{}{\{ t_i \mapsto \top \}}$ from the thread library. We can then define $\mutexperm{t}{A} \triangleq \ownGhost{}{\{ t \mapsto A \}}$, and see that each thread $t_i$ begins with $\mutexperm{t_i}{\top}$. The disjoint set algebra gives us that $\ownGhost{}{\mutexperm{t}{A \uplus B}} \dashv\vdash \ownGhost{}{\mutexperm{t}{A}} \ast \ownGhost{}{\mutexperm{t}{B}}$ (where $A \uplus B$ is only defined if $A$ and $B$ are disjoint), so a thread can split off permissions for a specific name or set of names $B$. Then we can implement $\notlocked{\gamma}{t}{q}$ as precisely $\ownGhost{}{\mutexperm{t}{\mutexname{\gamma}}} \ast \token{\gamma}{q}$. This gives us the properties required in Section~\ref{mutex-spec}: $\notlocked{\gamma}{t}{q_1} \ast \notlocked{\gamma}{t}{q_2} \vdash \mathsf{False}$ because $\ownGhost{}{\mutexperm{t}{\mutexname{\gamma}}} \ast \ownGhost{}{\mutexperm{t}{\mutexname{\gamma}}}$ (by disjointness), and $\mutexperm{t}{\mutexname{\gamma}} \ast \token{\gamma}{q} \dashv \vdash \notlocked{\gamma}{t}{q}$ by definition.
When a thread $t$ wants to interact with a mutex $\gamma$, it separates $\mutexperm{t}{\mutexname{\gamma}}$ from its set and uses it as permission to acquire $\gamma$; this is possible as long as $t$ has not already used $\mutexname{\gamma}$. %more on namespaces?

We consider two spinlock implementations of \lstinline{std::mutex}. The first, in Figure~\ref{mutex-impl1}, is a straightforward implementation similar to that used in HeapLang: \lstinline{lock} atomically exchanges \lstinline{true} with the current value of \lstinline{lock}, which is \lstinline{true} if the mutex is currently held (in which case the exchange does nothing and the loop continues) and \lstinline{false} if the mutex is not held (in which case the exchange sets \lstinline{lock} to \lstinline{true} and the loop ends). Unlike in HeapLang, a location that will be accessed concurrently by multiple threads must explicitly be declared to be of an \lstinline{atomic} type: data races on non-atomic locations are undefined behavior in C++. The second implementation, in Figure~\ref{mutex-impl2}, additionally records the thread ID of the current owner, and uses it to assert some of the mutex requirements: a thread calling \lstinline{unlock} must be the current owner, and when the mutex is destroyed it must not be held by any thread. (Because \lstinline{owner} is only accessed by the thread that holds the mutex and in the destructor, it does not need to be atomic.) Both of these implementations meet the informal specification of \lstinline{mutex}: since violating the mutex requirements is undefined behavior, assert failure and abnormal termination is a permissible result. However, the second implementation does \emph{not} meet the usual separation logic specification of locks, in which any thread that holds a transferable $\mathsf{locked}$ predicate can release the lock. We prove that both of these implementations satisfy the mutex specifications of Section~\ref{mutex-spec}. We outline the proof for \lstinline{Mutex2}; the proof for \lstinline{Mutex1} is strictly simpler.

The standard Iris approach to verifying a spinlock is to define an invariant of the form
\[
  \knowInv{}{\begin{aligned}
    &(\texttt{lock} \mapsto \mathsf{true}) \\
    {}\vee{} &(\texttt{lock} \mapsto \mathsf{false} \ast P \ast \token{\gamma})
  \end{aligned}},
\]
where whenever the lock is not held the invariant contains the protected resources $P$ and some exclusive token $\token{\gamma}$, and when the lock is held, these are transferred to the holder. Having $\token{\gamma}$ allows the thread to unlock the mutex: when it opens the invariant, it must be the unlocked branch because there cannot be two copies of $\token{\gamma}$. The mutex invariant is slightly more complex:\footnote{We use a cancelable invariant instead so that the invariant can be "deallocated" and the protected resources unboxed in the mutex destructor.\kedu{The \lstinline|cinv_own| detail should probably be omitted?} }
\[
  I(P) \triangleq \knowInv{}{\begin{aligned}
    &(\exists t.\ \ownGhost{}{\authfull t}) \\
    &{}\ast \left(\begin{aligned}
      &(\texttt{lock} \mapsto \mathsf{true}
        \ast \notlocked{\gamma}{t}) \\
      {}\vee{} &(\texttt{lock} \mapsto \mathsf{false} \ast P
        \ast \ownGhost{}{\authfrag \bot}
        \ast \texttt{owner} \mapsto \bot)
    \end{aligned}\right)
  \end{aligned}}
\] %don't reuse \gamma, or explain that it's a record

First, the locking thread $t$ hands over its $\notlocked{\gamma}{t}$ in the invariant. As mentioned before, this ensures the mutex is only destructed when no thread currently locks it. But when $\notlocked{\gamma}{t}$ is stored in the invariant, its argument $t$ is forgotten, so we use a pair of \textit{authoritative} ghost states $\ownGhost{}{\authfull t}$ and $\ownGhost{}{\authfrag t}$ to remedy this: when a thread $t$ locks the mutex, it also receives $\ownGhost{}{\authfrag t}$ from the mutex \kedu{Do we want to explain ghost update?} with the same $t$; the other piece $\ownGhost{}{\authfull t}$ always store the same value as $\ownGhost{}{\authfrag t}$ and is stored in the invariant, so when thread $t$ unlocks the mutex, it can use $\ownGhost{}{\authfrag t}$ to recover $\notlocked{\gamma}{t}$. The $\ownGhost{}{\authfrag t}$ ghost state is also exclusive and does the job of $\token{\gamma}$. Lastly, the \lstinline{owner} field is also a protected resource, and it is required to have the default value $\bot$ when the mutex is unowned.

Threads must check whether they already hold the recursive mutex before locking \lstinline{m}, so the \lstinline{owner} field may be accessed concurrently and must be atomic.
