predicate $P$ about location $\ell$. The fractions can be combined:
$\ell \mapsto_{\pi_1} P \ast \ell \mapsto_{\pi_2} P \dashv\vdash \ell \mapsto_{\pi_1 + \pi_2} P$.

We begin by examining \lstinline{std::mutex}, the basic lock class. The class contains methods \lstinline{lock}, \lstinline{unlock}, and \lstinline{try_lock}\footnote{The specification of \lstinline{try_lock} is just that of \lstinline{lock} plus the possibility that nothing changes, so we elide it in this paper.} as well as a constructor and destructor. The intended behavior is to provide mutual exclusion; a simple implementation could be a spinlock as shown in Figure~\ref{mutex-simple}, although more realistic implementations use OS primitives for efficiency. While \lstinline{std::mutex} is the library class corresponding to a standard lock, its official informal specification~\cite{ISO:2024:IIP} has three restrictions that do not appear in the standard separation logic treatment:
\begin{enumerate}
\item When a thread calls \lstinline{unlock}, it must own the mutex (i.e., it must have been the thread that most recently called \lstinline{lock}).
\item When a thread calls \lstinline{lock}, it must \emph{not} own the mutex.
\item When a mutex is destroyed, it must not be owned by any threads.
\end{enumerate}
A program that violates any of these conditions has \emph{undefined behavior} (i.e., it is erroneous and cannot be guaranteed to run correctly), so our program logic must ensure that they are respected.

Property 3 is the simplest from a separation logic perspective: we can define a fractional resource $\token{}{q}$ that a thread must give up in order to acquire the mutex, and require the full $\token{}{1}$ in the precondition of the destructor. The first two properties are more complicated, since they check whether a thread performing an operation is \emph{the same thread} as one that performed a previous operation. Our basic approach is to define predicates $\notlocked{}{t}{q}$ and $\locked{}{t}{q}$ such that a thread $t$ exchanges $\notlocked{}{t}{q}$ for $\locked{}{t}{q}$ when acquiring the mutex, and vice versa when releasing it. If we require that $\mathsf{not\_locked}$ is exclusive, i.e., $\notlocked{}{t}{q_1} \ast \notlocked{}{t}{q_2} \vdash \mathsf{False}$, then we have that each thread can only try to acquire a mutex once before releasing it.
However, the $\mathsf{m\_locked}$ and $\mathsf{not\_locked}$ predicates, like any other CSL predicate, can be transferred between threads: how can we ensure that the thread that owns $\notlocked{}{t}{q}$ is actually thread $t$? For this, we use BRiCk's non-transferable predicate $\currentthread{t}$ described in Section~\ref{brick}: a thread must own both $\currentthread{t}$ and $\notlocked{}{t}{q}$ (resp. $\locked{}{t}{q}$) to acquire (resp. release) the mutex, proving that it is the thread identified by the predicate. \ignore{These predicates satisfy the following properties:
\begin{align}
\notlocked{}{t}{q_1} \ast \notlocked{}{t}{q_2} \vdash \mathsf{False} \\ %\notlocked{\gamma}{t} \ast \locked{\gamma}{t} \vdash \mathsf{False} \and
\locked{}{t_1}{q_1} \ast \locked{}{t_2}{q_2} \vdash \mathsf{False}
\\ \token{}{1} \ast \locked{}{t}{q} \vdash \mathsf{False} %anything else we need?
\end{align}
Property 1 guarantees that a thread holding $\mathsf{not\_locked}$ actually does not hold the lock, property 2 guarantees mutual exclusion, and property 3 guarantees that full ownership of the token implies the lock is not owned by any thread.}

How does a thread obtain $\notlocked{}{t}{q}$ to begin with? We could explicitly specify a set of threads that are allowed to use a mutex when it is created, but we may not know this set of threads in advance and it may even be unbounded (e.g., if we spawn threads in a loop). Instead, we make it possible for a thread $t$ to \emph{register} itself with an existing mutex and obtain $\notlocked{}{t}{q}$, as long as $t$ can guarantee that it is not already registered with that mutex.

However, the need to show that the mutex is not already registered presents a further problem. The standard Iris specification for lock creation looks like $\{ \later P \}\ \texttt{makelock}()\ \{ \ell.\ \exists \gamma.\ \ell \mapsto \mathsf{lock}_\gamma(P) \}$, where $\gamma$ is an identifier for the lock. By the rules of separation logic, full ownership of $\ell \mapsto \mathsf{lock}_\gamma(P)$ implies that $\gamma$ is different from the identifier of any other lock, but once ownership of $\mathsf{lock}_\gamma$ is split up and distributed among threads, the threads are no longer able to prove that any two $\gamma$s are distinct. We solve this problem using \emph{namespaces}, which Iris uses to distinguish invariants; our approach is particularly close to Iris's handling of non-atomic invariants. Each mutex is identified by a combination of a statically chosen namespace $N$ and a dynamically chosen identifier $\gamma$, written as $\mutex{N, \gamma}{P}$. Our mutex constructor spec looks like \[\{\later P\}\ \texttt{mutex()}\ \{m.\ \exists \gamma.\ m \mapsto \mutex{N, \gamma}{P} \ast \token{\gamma}{1}\}\]
The constructor returns a pointer $m$ to the new $\mathsf{mutex}_{N, \gamma}$ as well as full ownership of the token; the caller is free to choose $N$, while $\gamma$ is existentially quantified. Each thread can acquire at most one lock from each namespace $N$ at a time, while the $\gamma$ allows the creation of a dynamically determined number of mutexes (e.g., in a loop with unknown bounds).

With this naming scheme established, we can require threads to register themselves mutex before using it. Each thread holds a set of as-yet-unregistered mutex names $\mutexperm{t}{A}$. A thread is created with its own $\currentthread{t}$ and the universe of possible mutex names $\top$:
\[ \{ \{\currentthread{t} \ast \mutexperm{t}{\top} \ast P\}\ \texttt{f()}\ \{Q\} \ast P\}\ \texttt{thread(f)}\ \{ p.\ p \mapsto \mathsf{thread}(Q) \}
\]
When $t$ wishes to register with a mutex in $N$, it removes $N$ from $A$ and exchanges it (along with a share of $\mathsf{token}$) for $\mathsf{not\_locked}$:
\begin{align*}
  \mutexperm{t}{A \uplus B} & \dashv\vdash \mutexperm{t}{A} \ast \mutexperm{t}{B} \\
  \mutexperm{t}{N} \ast \token{\gamma}{q} & \dashv \vdash \notlocked{N, \gamma}{t}{q}
\end{align*}
(where $A \uplus B$ is only defined if $A$ and $B$ are disjoint).
When a thread is finished using the mutex (and does not currently hold it), it can perform the same operation in reverse to recover $\mutexperm{t}{N}$ and $\token{\gamma}{q}$.
Each of our mutex types will use this same registration pattern and the same $\mathsf{not\_locked}$ predicate, though the form of their $\mathsf{locked}$ predicate varies according to the mutex type. We explain the implementation of $\mathsf{mutex\_perm}$ and $\mathsf{not\_locked}$ in Section~\ref{login}.

Using the $\mathsf{m\_locked}$ and $\mathsf{not\_locked}$ predicates, we can specify the mutex as follows:
\[\begin{array}{c}
\{\later P\}\\ \texttt{mutex()}\\ \{m.\ \exists \gamma.\ m \mapsto \mutex{N, \gamma}{P} \ast \token{\gamma}{1}\} \vspace{1em}\\\{\currentthread{t} \ast m \mapsto_\pi \mutex{N, \gamma}{P}\ast\notlocked{N, \gamma}{t}{q}\}\\ {\texttt{m.lock()}} \\ \{\currentthread{t} \ast m \mapsto_\pi \mutex{N, \gamma}{P}\ast\locked{N, \gamma}{t}{q}\ast P\}  \vspace{1em}\\
    \{\currentthread{t} \ast m \mapsto_\pi \mutex{N, \gamma}{P}\ast\locked{N, \gamma}{t}{q}
      \ast\triangleright P\}\\ {\texttt{m.unlock}()}\\
    \{\currentthread{t} \ast m \mapsto_\pi \mutex{N, \gamma}{P}\ast\notlocked{N, \gamma}{t}{q}\}  \vspace{1em} \\
\{m \mapsto \mutex{N, \gamma}{P} \ast \token{\gamma}{1}\}\\ \texttt{m.}\!\!\sim\!\texttt{mutex()}\\ \{P\}
\end{array}\]%% explain \pi for shares
The thread that constructs a mutex chooses a namespace $N$ for it, and receives an identifier $\gamma$ and ownership of $\mathsf{token}_\gamma$. Any thread that gets a share of the token and is not already using the namespace $N$ can register and receive $\notlocked{N, \gamma}{t}{q}$. To acquire the mutex, a thread $t$ needs to own some share $\pi$ of the mutex and can then exchange $\notlocked{N, \gamma}{t}{q}$ for $\locked{N, \gamma}{t}{q}$, while \lstinline{unlock} reverses the exchange%, and the laws of $\mathsf{m\_locked}$ and $\mathsf{not\_locked}$ ensure that no two threads hold the mutex at once and that a thread cannot simultaneously be $\mathsf{m\_locked}$ and $\mathsf{not\_locked}$
. Finally, $\token{\gamma}{1}$ in the precondition of the destructor ensures that no thread holds the mutex before deallocation.

\subsection{\texorpdfstring{\lstinline{std::recursive_mutex}}{std::recursive\_mutex}}
\emph{Recursive} or \emph{reentrant} mutexes can be acquired multiple times by the same thread, and only become available to another thread once every acquire has been matched with a release. Recursive mutexes are popular in object-oriented programming, allowing a method to acquire a lock every time it is called even if it is called from another locked method. %A canonical recursive mutex implementation is shown in Figure~\ref{rmutex-simple}. When no thread holds the lock, \lstinline{count} is 0 and \lstinline{owner} is \lstinline{std::thread::id()} (a default ID belonging to no thread). When a thread that does not already own the lock tries to acquire it, it calls the \lstinline{lock} method of an underlying conventional mutex; likewise, when the owner releases the lock for the last time (\lstinline{count} is 1), it \lstinline{unlock}s the underlying mutex. However, when the owner re-acquires a lock it already owns, it performs no synchronization operations, instead simply incrementing the count---and likewise, a non-final release simply decrements the count.
This avoids redundant synchronization and deadlock while still providing mutual exclusion.
Unlike basic mutexes, a recursive mutex cannot be implemented without tracking the owner's thread ID: if thread $t$ owns a recursive mutex, then $t$ alone can acquire it again, while any other thread attempting to acquire it will block. There is no way for $t$ to pass ownership of the recursive mutex to another thread, and no applicable concept of daring concurrency. Thus, there is no useful way to specify recursive mutexes without a thread-tracking discipline. %pull back on this a little?

The specification of a recursive mutex in separation logic requires some care, since acquiring/releasing the mutex may or may not obtain/give up the lock resources depending on how many times the caller has previously acquired it. While we could give specifications that explicitly distinguish the two cases, this is contrary to the intended abstraction---the point of a recursive mutex is that whether or not we hold the mutex before acquiring it, we know that we hold it afterwards, and as long as we perform the same number of releases as acquires we do not need to account for whether we still hold the lock. %note the existence of both atomic and invariant-based specs, and their relationship?

We accomplish this by combining the $\mathsf{not\_locked}$ and $\mathsf{locked}$ predicates of the mutex into a single predicate $\acquirable{N, \gamma}{t}{n}{q}{P}{a}$, where $n$ is the number of times (0 or more) that $t$ holds the mutex. When $n$ is 0, $\mathsf{holds}$ is precisely $\mathsf{not\_locked}$, ignoring $P$ and $a$. When $n$ is greater than 0, $\mathsf{holds}$ is analogous to $\mathsf{m\_locked}$, and the owner can borrow the resources $P$ from it:
\[\inferrule{n > 0}{\acquirable{N, \gamma}{t}{n}{q}{P}{a} \vdash P(a) \ast (\forall b.\ P(b) \wand \acquirable{N, \gamma}{t}{n}{q}{P}{b})}\]
This rule also illustrates the role of the argument $a$. Protected resources are often existentially quantified, e.g., $\exists v.\ x \mapsto v$, which interacts poorly with borrowing: a thread that holds the lock has complete control over the value $v$, but returning and then re-borrowing the resource will re-quantify over $v$, losing track of whatever value it currently has. We solve this by making $P$ a predicate on an arbitrary argument type, and making the current argument value $a$ a parameter to $\mathsf{holds}$; as long as a thread holds the mutex it knows the exact value of $a$, but when $n = 0$ the value of $a$ is arbitrary and gives no information about the state of the protected resources. %return to this explanation

Using $\mathsf{holds}$, we can specify \lstinline{lock} and \lstinline{unlock} as simply increasing and decreasing $n$, respectively:
\[\begin{array}{c}
\{\currentthread{t} \ast m \mapsto_\pi \rmutex{N, \gamma}{P}\ast\acquirable{N, \gamma}{t}{n}{q}{P}{a}\}\\ {\texttt{m.lock()}} \\ \{\currentthread{t} \ast m \mapsto_\pi \rmutex{N, \gamma}{P}\ast \exists a'.\ \mathsf{acquire}(n, a, a') \ast \acquirable{N, \gamma}{t}{n+1}{q}{P}{a'}\}  \vspace{1em}\\
    \{\currentthread{t} \ast m \mapsto_\pi \rmutex{N, \gamma}{P}\ast\acquirable{N, \gamma}{t}{n+1}{q}{P}{a}\}\\ {\texttt{m.unlock}()}\\
    \{\currentthread{t} \ast m \mapsto_\pi \rmutex{N, \gamma}{P}\ast\acquirable{N, \gamma}{t}{n}{q}{P}{a}\}
\end{array}\]
where $\mathsf{acquire}(n, a, a') \triangleq (n > 0 \Rightarrow a' = a)$ allows the argument $a$ to change arbitrarily if the caller of \lstinline{lock} did not already own the lock, but enforces that $a$ is unchanged if the caller did already own the lock. Other than that, these specifications are entirely agnostic to whether any given call is the first \lstinline{lock} or last \lstinline{unlock} on the mutex: we can thus reason about a method that acquires a recursive mutex, manipulates the associated resources, and releases the mutex without ever having to do case analysis on whether the caller already owned the mutex.

Figure~\ref{rmutex-ex-proof} shows an example of the use of \lstinline{recursive_mutex}. The mutex \lstinline{m} protects both \lstinline{balance_a} and \lstinline{balance_b}, and is acquired in each of their update methods. The \lstinline{transfer} method transfers the amount \lstinline{x} from \lstinline{balance_b} to \lstinline{balance_a} atomically---no other client should be able to observe a state in which \lstinline{balance_a} has been increased by \lstinline{balance_b} has not been decreased---so \lstinline{transfer} also acquires \lstinline{m}. The \lstinline{update_a} and \lstinline{update_b} methods may be called either from inside \lstinline{transfer} or directly by a client; the recursive mutex allows them to safely acquire \lstinline{m} in either case, and restore it to its previous state before returning.

In this example, the protected resources are $P(a, b) \triangleq \texttt{balance\_a} \mapsto a \ast \texttt{balance\_b} \mapsto b$. The specifications of \lstinline{update_a} and \lstinline{update_b} illustrate the dual meaning of the $\mathsf{holds}$ predicate's argument: if the caller already owns \texttt{m} then it learns that the value of \lstinline{balance_a} or \lstinline{balance_b} has been increased, while if it does not then it loses ownership of $P$ and the argument values give no information. In the body of \lstinline{transfer}, because we have already \lstinline{lock}ed \lstinline{m}, we know the precise values of \lstinline{balance_a} and \lstinline{balance_b} and can guarantee that they are $a + x$ and $b - x$ before \lstinline{unlock}ing.

\subsection{\texorpdfstring{\lstinline{std::shared_mutex}}{std::shared\_mutex}}
\label{shared-mutex}

C++'s \lstinline{shared_mutex} class is more commonly known as a \emph{reader-writer lock}. It provides two separate pairs of acquire and release operations, \emph{exclusive} \lstinline{lock}/\lstinline{unlock} and \emph{shared} {\lstset{breakatwhitespace}\lstinline{lock_shared}/\lstinline{unlock_shared};} while \lstinline{lock} and \lstinline{unlock} ensure mutual exclusion, any number of threads can successfully perform \lstinline{lock_shared} at once as long as no thread has acquired the lock exclusively. Reader-writer locks have been modeled in separation logic by \citet{heaplang-rw-lock}, and we build on their work, but must also account for C++'s additional restrictions: no thread may acquire shared ownership of the mutex more than once, only threads that have acquired it may release it, and a thread that acquired exclusive ownership through \lstinline|lock()| cannot call \lstinline|unlock_shared()| and vice versa.

Following \citet{heaplang-rw-lock}, we take the resource $P$ protected by a shared mutex to be a fractional predicate;
calling \lstinline{lock} yields full ownership of the resource $P(1)$,
while calling \lstinline{lock_shared} yields $P(q_P)$ for an arbitrary fraction $q_P$,
representing read-only access to $P$.
Accordingly, in our specifications each user of a shared mutex has one of three predicates, $\notlocked{N, \gamma}{t}{q}$, $\smreaderlocked{N, \gamma}{t}{q}{q_P}$, or $\smlocked{N, \gamma}{t}{q}$, where $\mathsf{sm\_reader\_locked}$ records the fraction $q_P$ of ownership received by the reader.

\[
\begin{array}{@{}c@{}}

\section{Implementing the Mutex Specifications}
Our specifications of C++ mutexes capture the informal specifications of the mutexes and can be used to verify client programs. Ideally, we would next show that standard library implementations actually meet our specifications. However, the widely used implementations of the C++ standard library would be difficult to verify---they use Pthread implementations of the corresponding mutex types, which have nearly the same specifications as the standard library mutexes, and the Pthread implementations in turn make heavy use of operating system primitives with complicated low-level specifications (e.g., Linux's \lstinline{futex}). In this section, we instead verify simple and portable implementations of the mutexes that synchronize using atomic operations instead of OS primitives. We first describe the ghost state construction that underlies the $\mathsf{locked}$ and $\mathsf{not\_locked}$ predicates for each mutex, and then show that our simple implementation of each mutex meets the specifications of the previous section. Beyond proofs, we also determined that our implementations pass all 17 of the test cases for mutexes\footnote{This does not include the tests for timed mutexes.} in the libc++ test suite\cite{libcpp-tests}.

\subsection{The Mutex Permission Construction}
\label{login}

All three of our mutex specifications use thread-specific predicates ($\mathsf{not\_locked}$, $\mathsf{m\_locked}$, $\mathsf{holds}$, etc.) to enforce the mutexes' requirements on thread behavior. In this section we describe a general ghost construction that we use to implement all of our thread-specific predicates. In order to register itself with a mutex and obtain its $\mathsf{not\_locked}$ predicate, a thread needs to prove that it does not own that mutex: in separation-logic terms, it needs to own a resource demonstrating that it is not the current holder of the mutex. This means that each thread must own, or be able to create, a not-the-owner resource (call it a ``mutex permission'') %name?
for every mutex it does not currently hold. We model this using an assertion $\mutexperm{t}{A}$, where $A$ is a set of possible mutex names\footnote{This pattern is not actually specific to mutexes; if another language feature required thread tracking, it could use the same set of namespaces and $\mutexperm{t}{A}$ assertion, rather than adding another such assertion.};
each thread begins with $A = \top$.

In Iris, we can implement this assertion using resource algebras (RAs), specifically the RA of functions from thread IDs to disjoint infinite sets. The thread creation library holds the resource $\ownGhost{}{\lambda t.\ \text{if } t \in T \text{ then } \emptyset \text{ else } \top}$, where $T$ is the set of currently existing thread IDs; each time we spawn a new thread $t_i$, we add $t_i$ to $T$ and withdraw the singleton function $\ownGhost{}{\{ t_i \mapsto \top \}}$ from the thread library. We can then define $\mutexperm{t}{A} \triangleq \ownGhost{}{\{ t \mapsto A \}}$, and see that each thread $t_i$ begins with $\mutexperm{t_i}{\top}$. The disjoint set algebra gives us that $\mutexperm{t}{A \uplus B} \dashv\vdash \mutexperm{t}{A} \ast \mutexperm{t}{B}$ (where $A \uplus B$ is only defined if $A$ and $B$ are disjoint), so a thread can split off permissions for a specific name or set of names $B$. Then we can implement $\notlocked{N, \gamma}{t}{q}$ as precisely $\mutexperm{t}{\mutexname{N}} \ast \token{\gamma}{q}$. This gives us the properties required in Section~\ref{mutex-spec}: $\notlocked{N, \gamma}{t}{q_1} \ast \notlocked{N, \gamma}{t}{q_2} \vdash \mathsf{False}$ because $\mutexperm{t}{\mutexname{N}} \ast \mutexperm{t}{\mutexname{N}} \vdash \mathsf{False}$ (by disjointness), and $\mutexperm{t}{\mutexname{N}} \ast \token{\gamma}{q} \dashv \vdash \notlocked{N, \gamma}{t}{q}$ by definition.
When a thread $t$ wants to interact with a mutex $N$, it separates $\mutexperm{t}{\mutexname{N}}$ from its set and uses it as permission to acquire $N$; this is possible as long as $t$ has not already used $\mutexname{N}$. In other words, $\mathsf{mutex\_perm}$ allows each thread to register for each mutex exactly once, as long as we choose distinct namespaces for the mutexes.

We consider two spinlock implementations of \lstinline{std::mutex}, shown in Figure~\ref{mutex-impl}. The first is a straightforward implementation similar to that used in HeapLang: \lstinline{lock} atomically exchanges \lstinline{true} with the current value of \lstinline{lock}, which is \lstinline{true} if the mutex is currently held (in which case the exchange does nothing and the loop continues) and \lstinline{false} if the mutex is not held (in which case the exchange sets \lstinline{lock} to \lstinline{true} and the loop ends). Unlike in HeapLang, a location that will be accessed concurrently by multiple threads must explicitly be declared to be of an \lstinline{atomic} type: data races on non-atomic locations are undefined behavior in C++. The second implementation additionally records the thread ID of the current owner, and uses it to assert some of the mutex requirements: a thread calling \lstinline{unlock} must be the current owner, and when the mutex is destroyed it must not be held by any thread. (Because \lstinline{owner} is only accessed by the thread that holds the mutex and in the destructor, it does not need to be atomic.) Both of these implementations meet the informal specification of \lstinline{mutex}: since violating the mutex requirements is undefined behavior, both nontermination and assertion failure are permissible results. However, the second implementation does \emph{not} meet the usual separation logic specification of locks, in which any thread that holds a transferable $\mathsf{locked}$ predicate can release the lock. We prove that both of these implementations satisfy the mutex specifications of Section~\ref{mutex-spec}. We outline the proof for \lstinline{Mutex2}; the proof for \lstinline{Mutex1} is strictly simpler.

The standard Iris approach to verifying a spinlock is to define an invariant of the form
\[\knowInv{}{(\texttt{lock} \mapsto \mathsf{true})    {}\vee{} (\texttt{lock} \mapsto \mathsf{false} \ast P \ast \mathsf{token}_\gamma)}
\]
where whenever the lock is not held the invariant contains the protected resources $P$ and some exclusive token $\mathsf{token}_\gamma$, and when the lock is held, these are transferred to the holder. Having $\mathsf{token}_\gamma$ allows the thread to lock the mutex: when it opens the invariant, it must be in the unlocked branch because there cannot be two copies of $\mathsf{token}_\gamma$. The mutex invariant is slightly more complex:
\[
  I_{N, \gamma}(P) \triangleq \begin{aligned}
    &\exists o.\ \ownGhost{}{\authfull o} \\
    &{}\ast \left(\begin{aligned}
      &(\texttt{lock} \mapsto \mathsf{true}
        \ast \exists t, q.\ o = (t, q) \ast \notlocked{N, \gamma}{t}{q}) \\
      {}\vee{} &(\texttt{lock} \mapsto \mathsf{false} \ast P
        \ast \ownGhost{}{\authfrag \bot}
        \ast \texttt{owner} \mapsto \bot)
    \end{aligned}\right)
  \end{aligned}
\]

The mutex invariant must manage the thread ownership state of the mutex, including the associated token fraction $q$. For this we use the \emph{authoritative} ghost state pattern, which lets us define resources $\ownGhost{}{\authfull o}$ and $\ownGhost{}{\authfrag o}$ such that $\ownGhost{}{\authfull o_1} \ast \ownGhost{}{\authfrag o_2} \vdash o_1 = o_2$. In this case, $o$ is either $(t, q)$ if a thread $t$ with fraction $q$ holds the lock (i.e., it has acquired the lock using its registration $\notlocked{N, \gamma}{t}{q}$), or $\bot$ if no thread currently holds the lock. When a thread acquires the lock, it trades $\notlocked{N, \gamma}{t}{q}$ for $\ownGhost{}{\authfrag (t, q)}$. The acquiring thread also receives ownership of the \lstinline{owner} field of the mutex, so that it can safely check and change it. In sum, the resources owned by the thread that holds the lock are $\locked{N, \gamma}{t}{q} \triangleq \ownGhost{}{\authfrag (t, q)} \ast \texttt{owner} \mapsto t$.
%First, the locking thread $t$ hands over its $\notlocked{\gamma}{t}{q}$ to the invariant, ensuring that a thread never holds both $\mathsf{m\_locked}$ and $\mathsf{not\_locked}$ and that the mutex is only destructed when no thread currently locks it. But when $\notlocked{\gamma}{t}$ is stored in the invariant, its argument $t$ is forgotten, so we use a pair of \textit{authoritative} ghost states $\ownGhost{}{\authfull t}$ and $\ownGhost{}{\authfrag t}$ to remedy this: when a thread $t$ locks the mutex, it also receives $\ownGhost{}{\authfrag t}$ from the mutex \kedu{Do we want to explain ghost update?} with the same $t$; the other piece $\ownGhost{}{\authfull t}$ always store the same value as $\ownGhost{}{\authfrag t}$ and is stored in the invariant, so when thread $t$ unlocks the mutex, it can use $\ownGhost{}{\authfrag t}$ to recover $\notlocked{\gamma}{t}$. The $\ownGhost{}{\authfrag t}$ ghost state is also exclusive and does the job of $\token{\gamma}$. Lastly, the \lstinline{owner} field is also a protected resource, and it is required to have the default value $\bot$ when the mutex is unowned.

%Now we can define $\locked{\gamma}{t}$ as $\notlocked{\gamma}{t} \ast \texttt{owner} \mapsto t$. The representation predicate for \lstinline{mutex} is then essentially $p \mapsto_\pi \mutex{N, \gamma}{P} \triangleq \knowInv{}{I_{N, \gamma}(P)}_\pi$. %fix the points-to for the fields?

The simplest way to implement a recursive mutex is by combining an underlying non-recursive mutex \lstinline{m} with an integer \lstinline{count}: each thread's first acquire and last release of the recursive mutex (per critical section) are performed on \lstinline{m}, while all intervening operations by the same thread only increment and decrement \lstinline{count}. Threads must check whether they already hold the recursive mutex before locking \lstinline{m}, so the \lstinline{owner} field may be accessed concurrently and must be atomic\footnote{Because atomic objects are currently not supported in BRiCk, in the formalization, the \lstinline|owner| field instead stores the \lstinline|std::hash| of the thread ID (which is a primitive type), and we additionally assume no hash collisions for the thread IDs. This is orthogonal to the contents of the paper.}.

Because the implementation includes both a mutex and an atomic field, the resources associated with the recursive mutex are divided across \emph{three} places: the mutex's protected resources, an invariant (containing atomically accessed resources), and the thread holding the lock (i.e., the $\mathsf{holds}$ predicate for $n > 0$). For a resource function $P$, these three parts are defined as follows:
\[\begin{array}{l}%vertical spacing
R_{}(P) \triangleq \texttt{count} \mapsto 0 \ast \ownGhost{}{\authfrag \bot} \ast \exists a.\ P(a) \vspace{.5em}\\
I_{N, \gamma}(P) \triangleq \exists o.\ \texttt{owner} \mapsto \mathsf{id}(o) \ast \ownGhost{}{\authfull o} \ast \text{if } o = (t, q) \text{ then } \locked{N, \gamma}{t}{q} \text{ else } \mathsf{emp}\vspace{.5em}\\
\acquirable{N, \gamma}{t}{n}{q}{P}{a} \triangleq \text{if } n = 0 \text{ then } \notlocked{N, \gamma}{t}{q} \text{ else } \texttt{count} \mapsto n \ast \ownGhost{}{\authfrag (t, q)} \ast P(a)\end{array}\]
The heart of the implementation proof is a piece of ghost state that tracks whether the recursive mutex is held; this state is either $\bot$ if it is not held, or $(t, q)$ if a thread holds $\locked{}{t}{q}$ of the underlying mutex \lstinline{m}. This ghost state is split using the authoritative pattern. The authoritative piece $\ownGhost{}{o}$ is held in the invariant $I$, where it determines the value of the \lstinline{owner} field ($t$ if there is an owner, or the default value \lstinline{std::thread::id()} if there is not). When no thread holds the recursive mutex, the inner mutex resources $R$ include the current \lstinline{count} (which must be 0), the ghost fragment (which must be $\bot$), and the protected resources $P$ at some argument $a$. When a thread acquires the inner mutex, it trades its $\notlocked{N, \gamma}{t}{q}$ for $\locked{N, \gamma}{t}{q}$ and $R$, giving it ownership of the \lstinline{count} field, the ghost fragment, and the protected resources $P(a)$; it then puts $\locked{N, \gamma}{t}{q}$ into the invariant $I$ and keeps the remaining resources, which constitute the non-0 case of $\mathsf{holds}$. This allows the thread that holds the lock to freely increment and decrement \lstinline{count} and borrow the resources $P(a)$, only returning them and retrieving $\locked{N, \gamma}{t}{q}$ when \lstinline{count} becomes 0 (after which it releases \lstinline{m} and returns to $\notlocked{N, \gamma}{t}{q}$). We can then define $\mathsf{rmutex}$ by
\[p \mapsto_\pi \rmutex{N, \gamma}{P} \triangleq p.\texttt{m} \mapsto_\pi \mutex{N, \gamma}{R(P)} \ast \knowInv{}{I_{N, \gamma}(P)}_\pi\]

The proof of \lstinline{lock} is particularly subtle. The precondition includes $\acquirable{N, \gamma}{t}{n}{q}{P}{a}$, but we must consider separately the cases where $n = 0$ and $n > 0$. If $n > 0$, then we have $\ownGhost{}{\authfrag (t, q)}$, which in combination with the invariant $I_{N, \gamma}(P)$ tells us that the value of the \lstinline{owner} field is exactly $t$, and so the condition of the \lstinline{if} will fail and we will simply increment the count (which we already own as part of $\mathsf{holds}$). On the other hand, if $n = 0$, then we have $\notlocked{N, \gamma}{t}{q}$, which in combination with the invariant $I_{N, \gamma}(P)$ tells us that $t$ \emph{cannot} be the current owner: $o$ may be $\bot$ or $(t', q)$, but if $t' = t$ then the invariant would hold $\locked{N, \gamma}{t}{q}$, which is inconsistent with $\notlocked{N, \gamma}{t}{q}$. Thus, in the 0 case the condition of the \lstinline{if} will succeed and we will acquire the underlying mutex \lstinline{m}, gaining access to the resources needed to increment \lstinline{count} and establish $\acquirable{N, \gamma}{t}{1}{q}{P}{a}$.

The proof of \lstinline{unlock} is simpler, since it can only be called by a thread with $\mathsf{holds}$ at $n + 1 > 0$; thus, the thread already owns \lstinline{count}, and needs only to check whether it has set \lstinline{count} to 0 and, if so, retrieve $\locked{N, \gamma}{t}{q}$ from the invariant and release \lstinline{m}.

class SharedMutex {
  std::atomic<int> sharers = 0;

  void lock(){
    int idle = 0;
    while(!sharers.compare_exchange_strong(idle, -1)) { idle = 0; }

  }

    sharers--;
  }

A shared mutex can be in one of three states: unheld, exclusively held (writer-locked), or shared (reader-locked). In the shared state it must also count the number of readers that hold it. This leads to an implementation with a single atomic counter, which is 0 when the lock is not held, -1 when it is held exclusively, and equal to the number of readers when it is shared (shown in Figure~\ref{smutex-simple}). It can only be taken exclusively (i.e., \lstinline{lock}ed) when the counter is exactly 0, but it can add a reader as long as the counter is not -1.

Recall from Section~\ref{shared-mutex} that the two \lstinline{lock} methods are specified as
\[\begin{array}{@{}c@{}}
\{\currentthread{t} \ast m \mapsto_\pi \smutex{N, \gamma}{P}\ast\notlocked{N, \gamma}{t}{q}\} \\
  \texttt{m.lock()} \\[-1pt]
\{\currentthread{t} \ast m \mapsto_\pi \smutex{N, \gamma}{P}\ast P(1)\ast\smlocked{N, \gamma}{t}{q}\} \\[1.8em]

\{\currentthread{t} \ast m \mapsto_\pi \smutex{N, \gamma}{P}\ast\notlocked{N, \gamma}{t}{q}\}\\
  \texttt{m.lock\_shared()} \\[-1pt]
\{\currentthread{t} \ast m \mapsto_\pi \smutex{N, \gamma}{P}\ast\exists q_P.\;\smreaderlocked{N, \gamma}{t}{q}{q_P} \ast P(q_P)\} \end{array}\]
Each thread that holds the mutex has two shares associated with it: the fraction $q$ from $\mathsf{not\_locked}$ (representing a share of the token used to ensure that there are no owners at deallocation), and the fraction $q_P$ of the protected resource $P$ (which is 1 for a writer and arbitrary for a reader). Thus, the state of the shared mutex can be modeled as a map from thread IDs to pairs of shares $(q, q_P)$. The central invariant of the shared mutex is then
\[  I_{N, \gamma}(P) \triangleq \begin{aligned}
    &(\exists n.\ \texttt{sharers} \mapsto n \\
    &{}\ast \left(\begin{aligned}
      &(\exists t, q.\ n = -1 \ast \ownGhost{}{\authfull \{t \mapsto (q, 1)\}} \ast \notlocked{N, \gamma}{t}{q}) \\
      {}\vee{} &(\exists M.\ n = |M| \ast \ownGhost{}{\authfull M} \ast P(1 - \mathsf{sum\_qP}(M)) \ast \Sep_{t \mapsto (q, \_) \in M} \notlocked{N, \gamma}{t}{q})
    \end{aligned}\right)
  \end{aligned}
\]
When the lock is exclusively held ($n =-1$), the map is a singleton $\{t \mapsto (q, 1)\}$, where thread $t$ has full ownership of $P$. Otherwise, the map has $n$ entries (possibly 0) and the invariant $I_{N, \gamma}(P)$ retains ownership of the remaining fraction $1 - \mathsf{sum\_qP}(M)$ of $P$, where $\mathsf{sum\_qP}(M)$ sums the $q_P$ components of all entries in $M$. In either case, $I_{N, \gamma}(P)$ also holds $\mathsf{not\_locked}$ for each thread that has acquired the lock in any way, ensuring that each thread can only attempt to acquire the shared mutex once. The shared mutex invariant resembles that of the basic mutex; in particular, note that when $n = 0$, the invariant reduces to $\ownGhost{}{\authfull \emptyset} \ast P(1)$.

The shared mutex $\mathsf{locked}$ predicates are simply fragments of the central map:
\[\begin{array}{l}
\smlocked{N, \gamma}{t}{q} \triangleq \ownGhost{}{\authfrag \{t \mapsto (q, 1)\}}\vspace{.5em}\\
\smreaderlocked{N, \gamma}{t}{q}{q_P} \triangleq \ownGhost{}{\authfrag \{t \mapsto (q, q_P)\}} \text{ where } q_P < 1
\end{array}\]
As in the basic mutex, the representation predicate is simply $p \mapsto_\pi \smutex{N, \gamma}{P} \triangleq \knowInv{}{I_{N, \gamma}(P)}_\pi$.

The proofs of the shared mutex specifications are also largely analogous to those of the basic mutex. The \lstinline{lock} and \lstinline{unlock} methods only transition between the $n = 0$ and $n = -1$ states; \lstinline{lock} spins until $n$ is 0, and the precondition $\smlocked{N, \gamma}{t}{q}$ of \lstinline{unlock} guarantees that $n$ is -1. On the reader side, \lstinline{lock_shared} and \lstinline{unlock_shared} stay within the second case of the invariant, adding or removing entries from $M$ and taking or returning the corresponding shares of $P$; \lstinline{lock_shared} spins when $n$ is -1, and the precondition $\smreaderlocked{N, \gamma}{t}{q}{q_P}$ of \lstinline{unlock_shared} is inconsistent with $n = -1$ (since we would then hold $\ownGhost{}{\authfull \{t \mapsto (q, 1)\}}$ and $\ownGhost{}{\authfrag \{t \mapsto (q, q_P)\}}$ where $q_P < 1$).
